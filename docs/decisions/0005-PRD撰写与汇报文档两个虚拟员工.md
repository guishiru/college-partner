# 0005 PRD撰写与汇报文档：写作类虚拟员工的确定性层

## 状态

已采纳。两个员工已开放，确定性层可用；大模型接入层未做。

## 背景

数据分析师之所以立得住，是因为它有一个**确定性引擎**：11 个统计方法口径固定，大模型只负责把需求翻译成方法和参数，不碰计算。

写 PRD 和写汇报稿看上去没有这样的引擎——产出是文字，价值在追问和判断。照这个思路做下去，这两个员工会退化成「一段提示词」：今天查出五个问题，明天查出三个，没人说得清它到底做了什么。

但仔细拆一遍会发现，它们的确定性层并不空。

## 决定

按数据分析师同样的三层结构建这两个员工。

**确定性层**——能机械判定的，全部进代码：

| PRD撰写 | 汇报文档 |
|---|---|
| 15 个必备章节缺没缺 | 表格合计行对不对 |
| 每条 FR 的触发/行为/验收齐不齐 | 声称穷尽的百分比加不加得到 100 |
| 验收条件含不含「流畅」「尽量」这类不可观察的词 | 写出来的算式算不算得出写下的结果 |
| 非功能需求有没有具体阀值 | 第一段是不是以铺垫句式开头 |
| 异常八类（空/错/加载/权限/并发/极端/存量/可逆）覆盖了几类 | 全文有没有出现要读者做什么 |
| 标了 `[假设]` 有没有收进假设索引 | 标题是不是只有「现状分析」这类类别词 |
| 标了 `[待确认]` 有没有进待确认清单 | 标题层级有没有超过三层 |
| 完备度闸门七项红黄绿 | 待补标注有没有带着发出去 |

**判断层**——需要理解内容的，一概不做：需求还原得对不对、范围切得合不合理、分组是否 MECE、结论对不对、排序逻辑是否一致。

**这条边界是有代价才划出来的。** 校验器一旦开始判断「这句是不是结论」「这两组是不是重叠」，就会产生它自己也解释不清的误报；而人对一个会误报的检查器的反应不是逐条甄别，是整体忽略。那时漏报也不会有人发现。宁可少查几项，也要保证报出来的每一条都站得住。

## 共用层

两个 skill 独立写成，但骨干是同一套：

- **先出骨架，停下来等确认**——都不允许一上来就出成稿
- **素材不够就标注，不要编**——PRD 叫三级标注，汇报叫「待补」
- **先问清缺口，不替用户猜**

所以抽出 `modules/skills/documents`：标注扫描、必备章节检查、markdown 表格解析、算术自洽、标题抽取与层级检查。两个员工各自只带自己的章节模板和质检规则。

## 关键取舍

**数据自洽先于结构诊断。** 算术错误比结构问题更急——读者验算一次发现错了，后面所有数字他都不会再信，这时结构再完美也没用。所以 `review_report` 第一件事是查算术。

**只报「对不上」，不报「数字本身对不对」。** 无法验证「本月质检单 164362 个」是不是真的，但能验证这个数在文中前后是否一致、算式算不算得出写下的结果。有一条测试专门守这条边界：一个离谱但自洽的数字不得被报错。

**校验器不评文风。** 同一份稿子换个语气，校验结论必须完全一样——有测试钉着。把口语化的周报改成公文腔是越界。

**「报告撰写专家」并入「汇报文档」。** 原先为数据分析报告设的那个角色和汇报文档职责重叠。合并后数据分析师的 `can_invoke` 指向汇报文档，分析结果交给它写成结论先行的汇报——这才是金字塔原理该起作用的地方。

## 影响

- 新增 `modules/skills/documents`、`modules/skills/prd_writer`、`modules/skills/report_writer`。
- `modules/employees` 开放「PRD撰写」与「汇报文档」，布局均为 `document_split`。
- 新增 33 条测试。每条规则配一对用例：一份触发它的坏稿，一份不该触发它的好稿。
