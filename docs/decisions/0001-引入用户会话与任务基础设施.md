# 0001 引入用户、会话与任务基础设施

## 状态

已采纳。

## 背景

第一个数据分析闭环跑通后，代码里出现了这样一个事实：

- `user_id` 和 `job_id` 在整个代码库中一次都没有出现。
- `session_id` 由前端 `crypto.randomUUID()` 生成，直接放进表单和请求体，服务端不做任何鉴权。
- `/api/reports/<session_id>/<report_id>/download` 只靠标识难猜来保护，知道两个标识的任何人都能下载他人报告。
- `DataAnalystWorkflow.execute(file_path, requirement)` 的签名里没有任何身份信息。

对照项目已有约定，以下四条都处于未实现状态：

- 用户数据必须绑定 user_id。
- 文件必须绑定 user_id、session_id、job_id。
- 不同用户之间禁止读取或覆盖数据。
- 任务失败后允许重试，但不能重复生成结果。

这些规则写在文档里，但没有任何代码在执行它们。

## 为什么现在做

身份是横切关注点，每个业务模块都要穿过它。现在只有一个业务模块，补一次即可；等到六个模块都上线再补，就要在六处分别穿线，还会产生六份互不一致的实现。这个成本随模块数量增长，越晚做越贵。

## 决定

新增三个叶子模块，各自拥有自己的表，互不依赖：

- `modules/users`：用户、用户状态、访问令牌。
- `modules/conversations`：会话及其归属。
- `modules/jobs`：任务生命周期、幂等键与重试规则。

另新增 `modules/workspace.py`，只负责解析运行时目录和状态库路径。它不是业务模块。之所以单独存在，是因为 Web 应用、管理员 CLI 和测试三个入口必须落在同一个数据库上；各自计算路径的结果是 CLI 创建的用户，Web 应用读不到。

存储选用标准库的 SQLite。理由：不引入新依赖；任务状态迁移需要事务，JSON 文件做不到；「同一任务不能产生两份结果」需要唯一约束来保证，靠应用层判断在并发下不成立。

## 关键取舍

**不做注册接口。** 用户由管理员通过 `python -m modules.users.cli create <username>` 创建。产品总纲把账号管理放在管理员职责下，开放注册端点等于让任何人自行获得身份。

**会话标识改由服务端生成。** 前端自带标识的设计让「会话属于谁」无从校验。

**会话不存在与会话属于他人返回同一句错误。** 区分两者会泄露某个会话确实存在且属于别人。

**工作流入口强制要求任务上下文。** 把 `JobContext` 做成必填参数，而不是可选参数或约定俗成的字典键，这样「忘记传身份」在调用时就不成立，不依赖 review 发现。

**三个模块接受少量 SQLite 连接样板重复。** 抽一个共享数据库工具会让三个模块产生共同依赖。当前选择保持模块独立，代价是约十五行重复。若第四、第五个模块出现同样样板，再重新评估。

## 影响

- `SessionFileStore.save_upload` 和 `resolve` 的签名增加 `user_id`。
- `DataAnalystWorkflow.inspect_and_plan` 和 `execute` 的签名增加 `context`。
- 所有会话范围内的 HTTP 接口都需要 `Authorization: Bearer <token>`。
- 前端新增令牌输入，进入工作区时向服务端申请会话；报告下载改为带令牌的 fetch。
- 新增 `tests/test_module_boundaries.py`，用 import 扫描把依赖方向固定下来。新增模块必须在其 `ALLOWED` 表中显式声明允许依赖谁。
