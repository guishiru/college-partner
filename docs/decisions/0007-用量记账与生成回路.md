# 0007 用量记账，以及让模型产出交付物的两道闸门

## 状态

已采纳。用量已落库；PRD撰写与汇报文档的生成层已通（骨架、成稿、校验回路、数字防线）。HTTP 层的写作接口尚未开。

## 一、用量记账

### 背景

接上语义识别后，每次调模型的 token 数算出来了，进了 HTTP 响应，然后**转手就扔**——`jobs` 表 13 个字段没有一个跟用量有关。这意味着「这个月谁花了多少」「哪个员工最烧钱」「某次结果反常时调了几次」这些问题一个都答不了。

加字段容易，补历史不可能。现在不存，三个月后想算账，前三个月永远缺一块。

### 决定

`jobs` 表加 `model` / `llm_calls` / `input_tokens` / `output_tokens` 四列，`record_usage` **累加而不是覆盖**——一个任务可能调多次模型：识别一次、成稿一次、校验没过再重写一次。覆盖的话账永远少算。

**任务失败也记账。** 钱已经花了。`record_usage` 不限制任务状态。

新增两个查询口径：`usage_for_session`（这个会话花了多少）和 `usage_for_user`（这个用户总共花了多少）。限额要按用户算——按会话算会被「新建一个会话」绕过，有一条测试盯着这点。

按 skill 分组的明细也一并返回，用来回答「哪个能力最烧钱」。

## 二、生成回路

### 为什么提示词不够

两个 skill 都写着「事实、数字只能来自用户给的材料，不要编」。规则写在提示词里，模型多半会守——但「多半」不是工程。

### 决定：两阶段 + 校验回路

产品约定「先出骨架，停下来等确认」，所以生成分两步，中间由用户拍板：

- `draft_skeleton()` 只出骨架。**这一步不跑校验器**——骨架本来就不完整，拿成稿的标准查它只会全红。
- `draft_document()` 成稿，然后进回路：出稿 → 校验 → 不过就把**问题清单原样递回**让模型重出全文。

校验器已经能指出「缺假设索引」「验收条件含流畅」「出现了清单外的数字」。把这些递回去比让人改快，也比在提示词里反复叮嘱有效——提示词是事前祈祷，校验是事后核对。

**重写有上限（默认 2 次）。** 模型改不动时会原地打转：同一条问题改三次还在，改三十次也一样，只是烧钱。到上限就停，把当前稿**加上未解决的问题清单**交还给用户——半成品配一份明确的问题列表，比一份看起来完整但暗藏问题的稿子有用。

## 三、数字防线

这是本次最值得说的一处。

代码先从材料里抽出**事实清单**，每条带出处；模型只能用清单里的数；成稿回来后扫描其中每个数字，不在清单里的整稿打回。

`fact_sheet_from_analysis()` 把分析结果转成清单，每条挂着产生它的 `job_id`。这是「报告只能引用已授权的分析结果」那条约定的落地形式：汇报文档拿到的不是一堆表，而是一份带出处的事实清单。

### 放过哪些数字

全查会淹在误报里，所以放过四类：章节号与条目号（`4.2`、`FR-003`）、小整数（0–12，「分三步走」这类计数和月份）、标注为 `[待确认]`/`[待补充]` 的行、`【待补：…】` 占位。

**放过小整数是个取舍**：它让「提升 3 倍」这种编造漏网。代价是确定的，收益是校验器不会因为满屏误报而被人整体忽略——后者更致命。要更严就调低 `small_number_limit`。

### 实测

给一份只含「7200」和「40」的清单，模型写出「预计增长 35%」：

```
第一版 → 拦下 35 → 带着问题清单重写 → 第二版通过（2 次调用）
模型改不动时 → 重写 2 次后停下，未解决 1 条，连同半成品交还
```
