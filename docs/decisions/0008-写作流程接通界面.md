# 0008 写作流程接通界面

## 状态

已采纳。PRD撰写与汇报文档在界面上可用。

## 做了什么

**分派表放在 `modules/skills/dispatch.py`。** Web 层不该知道「PRD撰写用哪个提示词、汇报文档用哪个校验器」。给它一张表：员工标识进来，骨架/成稿/审阅三个函数出去。新增写作类员工只动这张表。

第一版放在 `modules/skills/documents/` 里，立刻撞上循环依赖——共用层去 import 员工，员工又 import 共用层。层次是：共用校验层在底，两个员工在中，分派表在顶。

**三个接口**：`/api/documents/skeleton`、`/draft`、`/review`。分派按**会话绑定的员工**决定，不由请求指定——否则一个会话就能冒用另一个员工的能力。数据分析师的会话调写作接口返回 400。

**生成用量接上了 `record_usage`。** 无论成稿与否都记——重写三次没通过，钱一样花掉了。实测一次骨架加一次成稿，两条 skill 各自记账。

**右栏按员工换内容。** 文档型员工的右栏是「骨架待确认 / 成稿 / 交付前校验」三段，分析型员工仍是结果工作区。用 CSS 按 `data-layout` 切换。

## 路上踩的两个坑

**共用类名。** 新加的「确认骨架」按钮沿用了分析流程的 `confirm-button`，端到端立刻红了——`.last` 选中了隐藏的那一个。两个不相干的流程共用类名就是这个下场，改成独立 class。

**`hidden` 属性盖不住 `display:flex`。** 用 JS 给 `.chips` 设 `hidden` 没有效果，因为它自带 `display:flex`，优先级高于 UA 样式表的 `[hidden]`。改成跟其他栏一致的 CSS 驱动。

## 顺手修掉的硬编码

截图里发现对话栏的标题「分析对话」、副标题「先上传数据」、角标「11 methods」和首条欢迎语「你好，我是数据分析师」全是写死的——选了 PRD撰写之后还在说上传 Excel。这跟布局是同一类问题：**把某一个员工此刻的样子当成了产品的形状**。都改成随员工变，并加了断言钉住。

## 测试

端到端从 1 个流程变成 2 个：分析闭环照旧，另加写作流程——选 PRD撰写 → 布局切换 → 提需求 → 出骨架 → 确认 → 成稿 → 校验结果显示。两条路互不干扰。

CI 加了一步生成假模型回复。回复是刻意设计的：成稿**故意不合格**，这样校验回路和右栏的问题清单才会真的被走到。
